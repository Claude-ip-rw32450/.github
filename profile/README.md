<h2>二、T+0 到 T+1 小时：先分清是哪种限制</h2>
<p>「用不了」至少有四种情况：登录被拦、能登录但不能对话、能对话但订阅显示异常、网络层根本连不上。四种情况的处理路径完全不同，混为一谈会做很多无用功。</p>
<h3>四类现象怎么区分</h3>
<p>登录被拦会停在验证环节；能登录不能对话通常是权限或额度问题；订阅异常会在账单页有明确提示；网络层问题表现为页面打不开或超时，与账号无关。逐项确认一遍，通常十分钟内能定位。</p>
<h3>先排除自己这边的问题</h3>
<p>用另一条线路、另一台设备分别试一次。如果换设备就正常，问题在本地环境；如果换线路就正常，问题在出口；两者都换还不行，才考虑账号侧。这一步常被跳过，结果把本地网络抖动当成账号被封，白折腾一天。</p>
<h2>三、T+1 到 T+24 小时：修环境，别急着换号</h2>
<p>确认是账号侧或出口侧的问题后，正确的动作是把环境恢复到「上一次正常时的状态」。很多人直接换 IP 重试，环境里的矛盾点还在，换了也白换。</p>
<h3>三项比对：时区、语言、出口</h3>
<p>把当前环境的时区、Accept-Language、出口 ASN 与台账里记录的正常状态逐项对比。三项里有任何一项变了，先改回一致再试。这三项是最常见的漂移点，尤其是系统自动更新后时区被重置。</p>
<h3>改完不要立刻连续重试</h3>
<p>改完隔一段时间再试，一次不行就停手核查，别连点。连续重试会让行为记录出现密集的失败序列，把一次普通异常放大成持续异常。核查的顺序回到上一节：先本地、再线路、最后账号。</p>

<h2>四、T+24 小时到 T+3 天：换出口的正确做法</h2>
<p>环境和本地都排除了，再换出口。换出口不是随便找一条线，而是换一条「同地区、不同 ASN、信誉干净」的线。同地区保证归属一致，不同 ASN 避免同段邻居的影响，信誉干净避免刚换上去又撞上问题。</p>
<h3>换线的三个约束</h3>
<p>地区不变、ASN 不同、时段分散。地区不变是为了不让归属信息出现跳跃；ASN 不同是为了真正换一批网络；时段分散是避免在短时间内完成「换线加重试」的密集动作。三条都满足，才算一次合格的换线。</p>

<h3>订阅与数据要能续上</h3>
<p>换出口前先确认账号还能登录，能登录说明订阅与数据都还在，只是访问受限。如果连登录都不行，就该走平台官方申诉渠道，而不是继续换线。这一点要分清：换线解决的是环境问题，解决不了账号本身的处置。</p>
<h2>五、T+3 到 T+7 天：恢复期的节奏</h2>
<p>恢复后不要马上恢复满负荷。前三天保持低频使用，每天固定时段做一两次常规对话，观察是否稳定。三天无异常再逐步加到正常频率，一周后做一次复盘。</p>
<h3>复盘要看三个数</h3>
<p>异常发生前后的出口变化次数、环境参数变更记录、同类问题的历史次数。三个数写进台账，下次遇到类似情况可以直接对照，不用从零开始排查。</p>
<h3>什么情况下该放弃这个号</h3>
<p>如果按平台官方流程申诉后仍无法恢复，或者同一个号在两周内重复出现同类限制三次以上，继续投入的性价比就很低。这时换号是合理选择，但要同步检查环境，否则新号会重复同样的路径。</p>
<h2>常见问答</h2>
<h3>换个出口就一定能恢复吗？</h3>
<p>答：不一定。换出口只解决环境层面的问题，账号本身的处置需要按平台流程处理。先确认能否登录、订阅是否还在，再判断换线有没有意义，顺序反了会浪费很多时间。</p>
<h3>动态住宅 IP 每次都不一样，会不会更容易出问题？</h3>
<p>答：动态池的特点是地址会轮换，对只做读取的任务影响不大；对需要长期登录态的账号，建议在客户端配置里固定会话保持时长，让同一个会话尽量落在一个地址上，减少中途换地址。</p>
<h3>环境改回一致后要等多久再试？</h3>
<p>答：没有统一标准，经验上是隔几小时到半天，让记录有一个自然的间隔。频繁重试的代价通常比多等几小时更大，尤其是已经出现过一次限制的号。</p>
<h3>台账里应该记哪些字段，方便下次排查？</h3>
<p>答：出口地址与 ASN、时区、语言、UA 主版本、最近一次正常时间、异常现象与处理动作。六项足够，字段固定比字段多更重要，团队里所有人按同一套填，才能横向比较。</p>
